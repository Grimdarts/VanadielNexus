## Problem and intended experience

Players should customize gear, sets, settings, and controls without editing maintained job logic. Jason wants the same organization across all 22 jobs, neutral User/Player naming, and optional G13 support. His central requirement: "I want players to be able to edit these files easily."

A player defines an exact owned item once, reuses it across job sets, and can work in a text editor or through Nexus. A compact in-game G13 map matches the physical keypad, while its LCD shows useful job information. Neither device nor Nexus is required to play.

## Agreed premises and chosen approach

- Separate maintained behavior from player customization; common organization must allow specialized job behavior.
- SMN is the first playable reference, preserving current gameplay before research-driven improvements. Compare BLU and RUN during architecture design, not after finalizing the SMN structure.
- Multibox coordination is a separate experimental workstream requiring volunteer live testing. Jason does not multibox; a possible tester is not a committed resource.
- Chosen approach B: define the supported file format and ownership boundaries, check them against existing jobs, prove SMN parity, then implement displays and Nexus editing in stages. Extend the proven structure to other jobs afterward.
- Alternatives: Lua-first migration risks later format changes; editor-first prototype delays live gameplay verification. Both were considered; B was selected.

## Component boundaries

Exact filenames, folder layout, and integration points remain engineering-review decisions. These are responsibilities, not a promise of one file per row.

| Component | Ownership and purpose |
|---|---|
| Entry and loader | Maintained; select profile and job, validate required files, connect job logic |
| Common logic | Maintained; shared gear-selection helpers and lifecycle rules |
| Job logic | Maintained; specialized spells, abilities, pets, and job-state behavior |
| Equipment catalog | Character-owned; exact equipment identities, augments, and readable labels |
| Job sets | Character-owned; per-job set/slot assignments using catalog references or plain item names |
| Settings | Character-owned; shared defaults with per-job overrides |
| Keyboard hotkeys | Character-owned; shared defaults with per-job additions/overrides |
| G13 configuration and renderer | Optional; mappings separate from keyboard bindings, shared commands underneath |
| Automation | Optional; separate action-initiating routines and settings |
| Coordination addon | Optional experimental; same-PC group communication across job changes |
| Nexus | Optional; inspect, preview, save supported edits, or generate copyable Lua |

Built-in defaults < character shared settings < character job settings. Settings choose behavior; sets choose equipment. Define nested merge/replacement and explicit removal semantics before coding. Hotkeys need an explicit way to remove inherited bindings. Remove bindings owned by this system on unload/reload/job change; investigate collisions with bindings owned elsewhere rather than indiscriminately clearing them.

Multiple characters may run simultaneously on one PC. Profile identity must disambiguate characters, including server when needed; exact discovery is unresolved. Runtime state, pending work, display data, and writes must be associated with the correct character/session. Nexus and G13 require explicit character selection rules, still to be designed.

Missing REQUIRED profile files stop initialization with named missing files and setup instructions. No silent example gear or fallback to another character. Optional modules can be absent. Validate before enabling behavior and clean up any partially initialized resources on failure. Ship examples and a short setup guide.

## Gear catalog and supported editing format

- Distinct augmented copies are distinct records; do not merge by base item name.
- Use stable catalog record IDs with human-readable labels. These identify exact equipment records, not FFXI base item IDs; different augmented copies have different catalog record IDs. A label change must not break references. Precise ID creation and migrations remain to be specified.
- Plain item names are allowed for ordinary gear. Catalog references are preferred for exact augmented copies and centrally managed items.
- Validate references and set structure at load. Errors identify job, set, slot, and missing/invalid reference. Prevent a missing reference from quietly becoming an omitted slot.
- Define a small readable Lua data format for managed catalog and set sections. Specify allowed literals, references, comments, and how inherited/combined sets are represented. Do not promise arbitrary executable Lua round trips.
- Custom logic outside supported editable sections remains possible; unsupported structures use Nexus's copy workflow. Determine editable scope per operation, without silently rewriting other sections.

Nexus supports two workflows using the same intended change representation:

1. Select the character and owned item, including exact augmented copy; add/update its catalog record or assign it to a job-set slot.
2. Preview the change. Distinguish a one-slot assignment from an item-definition edit affecting multiple sets. List known consumers; show incomplete coverage if any sets cannot be inspected.
3. Save supported changes with backup, or copy Lua with destination instructions.

Proposed engineering protections, not yet implemented: minimal text edits preserving comments/custom sections, fresh source check to detect intervening manual edits, validation of resulting Lua and intended semantic change, and recoverable writes. A catalog-plus-set edit must not leave dangling references after a partial save. Exact patch/transaction strategy is an engineering gate.

This is new direct-save behavior for the managed bundle. It does not grant general write capability to the existing arbitrary-Lua Sets-page workflow. Lua remains usable without Nexus.

## G13 in-game overlay

Approved requirements:

- Preserve current SMN colors and font; current compact footprint is the target.
- Replace the text-column key listing with the correct physical G1-G22 row arrangement, stagger, and recognizable key shapes.
- Small G-numbers in consistent corners, action labels up to two lines, readable abbreviations when needed, full last-action detail.
- Modes and relevant job status around the key map. Preserve adjustability and saved position.
- Exclude thumbstick/thumb buttons; players map them in official Logitech software.
- Preserve the working M-button switching. M presses immediately change the in-game map.

Build a visual mockup at the current footprint before renderer implementation. Label fit and shaped drawing feasibility are unresolved; propose adjustments for review if they cannot coexist at that size. Do not silently shrink text or enlarge the panel. Exact shapes should be checked against the actual device/reference, not an approximate text sketch.

Verified existing path: G13-M-buttons.lua handles M_PRESSED for lhc, emits Ctrl+Alt+Shift+F1/F2/F3; Nova-Common binds those to gs c nova layer M1/M2/M3. Jason confirms this works live. Neutral naming must preserve this contract with compatibility aliases or an explicitly tested migration. No Logitech-script replacement is implied.

## Physical G13 LCD

- First two pages are job-specific; exact content split remains open.
- Existing world-information page moves to the LAST page button for every job, retaining Vana'diel day, moon phase, and existing world data. Inspect the applet before assuming a page-button count or other page contents.
- On job change, open the new job's first page.
- M1/M2/M3 changes controls and relevant indicators, while retaining the LCD page being viewed.
- Initial SMN content: avatar, layer, Rage/Ward recasts to tenths, temporary high-priority status such as Astral Conduit. Defaults may change with gameplay feedback.
- Shared renderer with per-job content definitions and character overrides. Unavailable or stale information must not appear as zero/ready.
- Both display surfaces consume consistent character state. The current applet's discovery, update protocol, and character selection require read-only inspection.

## Optional automation

Core gear selection remains active for player-initiated actions, buff/status changes, and selected modes. Optional automation initiates gameplay actions. A game event alone does not make action initiation core behavior. Player-triggered hotkey sequences remain explicit controls; audit delayed or repeating sequences carefully.

- Separate automation from maintained swap rules and player sets; internal job routines may be separate modules behind a clear entry point.
- Remember chosen settings and enabled preference per character/job. Restore only after valid current state; discard queued work from a prior session/job.
- Off cancels pending automated work; already-issued game actions may not be reversible and must be documented.
- Explicit take-control toggle pauses until resumed. Quick manual actions have priority; reevaluate afterward rather than replaying stale work.
- Visible Running/Paused/Off state and pause reason. Final state-machine rules are an engineering-review item.
- With automation absent or disabled, core swaps must work. Preserve current SMN behavior while identifying and separating any existing automatic action use; discuss conflicts before migration.

## Experimental same-PC multibox

Explicit group members and leader; roles configurable independently of jobs. No dependence on G13 or Nexus remaining open. Avoid broad all-session command recipients by default.

Agreed rules:

- Combat initiation configurable per group; default requires leader engagement or explicit attack command, not target selection alone.
- Target switching configurable; default follows leader's engaged target, with explicit-assist-only alternative.
- Each character opts into remote control. Leader may pause group and resume group-paused members; cannot override local Off or local manual-control pause.
- Leader unavailable: suspend new leader-dependent actions, discard pending leader commands; explicitly enabled local support may continue where its own conditions remain valid. Existing auto-attacks may continue; no automatic disengage promised.

Transport remains a proposal: Send for explicit commands plus native Windower IPC for state was suggested; Claude recommends investigating a single IPC transport first. Do not add both dependencies without evidence. Sender/recipient validation, stale-state expiry, readiness, and duplicate-command handling need specification before live coordination.

Release readiness requires real simultaneous sessions. Start with one leader and one support character available to a volunteer. BRD/GEO/WHM/RDM/SCH/DNC are candidates, not a single generic support routine. Define whether any pre-validation experimental artifact is distributed separately; do not bundle it as a ready/default feature. No committed test date.

## Stages and acceptance

1. File contract and inventory: inspect current SMN/BLU/RUN lifecycles, catalog usages, applet and renderer. Map representative sets without modifying installed jobs. Define ownership, syntax, schema versioning, overrides/removal, profile selection, validation, and migration boundaries.
2. SMN parity: back up and stage changes; compare resolved sets and augmented identities offline. Live checks cover load/unload/reload, job changes, representative summons/pacts and gear phases, modes, weapon locks, and separation from optional automation. Mock tests cannot establish game timing.
3. Display proof: approve shaped-map mockup at actual target size; implement and test M-button switching, labels, position/size persistence, LCD first-page-on-job-change and world-last behavior. Inspect actual applet first. Exact content defaults remain adjustable.
4. Nexus editor: prove add item, reuse across sets, single-slot replacement, shared-impact preview, save/copy equivalence, unsupported-file fallback, preservation of comments, conflicting manual edits, and backup recovery. If rebuilding Nexus, validate the actual staged/installed frozen executable with startup checks, not source tests alone.
5. Other jobs: migrate incrementally with job-specific validation, using researched improvements only after review. Support standalone play without optional components.
6. Experimental automation/coordination: specify and test independently, with live volunteer gate before readiness claims.

First-use failure and update tests must establish that required-profile errors are understandable and maintainer updates do not overwrite player files. Freeze exact update ownership before packaging.

## Distribution and deferred decisions

Goal: reusable bundles containing maintained code, example personal files, setup/update instructions, optional integrations, version manifest, and rollback guidance. Actual channel (manual archive, GitHub release, Nexus-assisted distribution) and build/publish pipeline are explicitly deferred. No publication, installation, automatic update, or final release channel is authorized here.

Open engineering decisions: file tree and supported syntax; loader adapters versus framework conversion; catalog IDs and rename/delete workflow; settings merge/removal; hotkey ownership and collisions; profile/server/session identity; LCD character selection and existing applet capabilities; editor transactions/concurrency; release channel. These are not reasons to reopen settled display taste choices.

## Changes during the build

Evaluate every request before implementing it. Clear small changes fitting the active stage may enter scope after explaining impact and recording the adjustment. Ease includes compatibility, persisted data, affected jobs, and validation, not line count alone.

Requests needing discussion or materially expanding scope go to a deferred-request record: desired outcome, reason, open questions, affected components, dependencies, and revisit trigger. They do not block the current stage unless they expose a defect in its assumptions. No unrequested features are silently added.
