## Problem Statement

Players keep their GearSwap sets in big hand-written Lua files: Jason's BLU alone is about 2,000 lines across three files. Finding every set that still uses an old piece, checking that a set's gear is actually in a wardrobe, and building a new set means reading Lua by hand.

The Set manager shows every set in a player's GearSwap files laid out like the in-game equipment menu. It flags upgrades and unreachable pieces, offers a picker of owned items that fit, and lets players build new and shared sets (including conditional ones) that the app writes into its own Lua file.

It is for every FFXI player on Windower 4, not just Jason. File styles differ per player.

In Jason's words: "You need to be able to pull up what sets are used in each of the players gearswap lua files this way they can be edited. The system is also going to need to cross reference what items are in the players inventory so you're able to swap out pieces with relevant items in your inventory. It will also need to be able to create sets from a blank canvas that you'd be able to add to the lua file."

## What Makes This Cool

- **Your sets, seen the way the game shows them.** A 4×4 grid (Main Sub Range Ammo / Head Neck Ear 1 Ear 2 / Body Hands Ring 1 Ring 2 / Back Waist Legs Feet), with real item icons pulled from the player's own game files.
- **It works on any file style.** The app runs the player's Lua the way GearSwap does instead of parsing its text. BLU's `nova_gear` variables, SMN's `set_combine` chains and other players' layouts all come out as plain resolved sets. The closest prior art, GearTree/GSUI (in-game addons that edit Lua in place), shows users hitting `set_combine` sets that display only the overlay, and "source unknown" errors on some files. Running the Lua avoids both.
- **"You got Hashishin Kavuk +3. These 4 sets still use +2. Copy all 4 fixes."**
- **Try it on in game.** "Equip now" sends `//gs equip <set path>` through the Nexus addon.
- **Bag warnings.** For example: "Sroda Ring is in your Mog Safe; GearSwap can't reach it."

## Constraints

- PySide6 desktop app, frozen with PyInstaller (`build.ps1`, GitHub Actions on release). Any new runtime dependency must survive the frozen build (`tools/check_frozen.py`).
- **lupa becomes a runtime dependency.** Today it is test-only and not in `requirements.txt`. GearSwap runs on Windower's LuaJIT (Lua 5.1 semantics), so the sandbox must use a Lua 5.1-compatible runtime.
- The app never edits a player's hand-written set definitions (decision D4 below). The only Lua it writes is its own generated file plus, with the player's OK, one `include` line per job file.
- Before touching anything in the Windower folder, back up (Jason: `C:\Users\Jason\Games\FFXI-Backups`; other players: the app's own backup folder) and check that the app isn't writing the same file.
- `data/` is Jason's player data: never committed, never overwritten in tests. Extracted icons are cached per machine and never shipped or committed.
- Follow `DESIGN.md`: navy/cyan/gold, one primary button per screen, a right-side detail panel, nothing smaller than 12px.
- GearSwap can only equip from Inventory and Wardrobes 1-8. Mog Safe, Storage, Locker, Satchel, Sack and Case are out of reach.

## Premises (agreed)

1. **Sets are read by running the player's Lua**, in a sandbox in the app with a mocked GearSwap/Windower host. They are not read by parsing text, and not with `//gs export`. Verified in `GearSwap/export.lua`: `export sets` flattens every set into one `sets.exported` list and drops set names.
2. **Pieces are matched by item ID plus augments** against the character's inventory snapshot, so augment variants (Herculean Helm WSD vs DT) stay distinct.
3. **(Revised after the Codex challenge.) Every set has two independent settings.** *Used by*: all jobs, a list of jobs, or one job, with the list always visible so a shared change never quietly reaches a job you didn't pick. *Worn*: normally, or "When…" through a rule card.
4. **Sets your Lua builds automatically at runtime** (NIN/COR/BST/RDM rescan from `Nova-GuideCandidates.lua`, or any player's equivalent) are shown read-only and labelled "picked automatically".
5. **Every write is backed up and undoable.** Icons come from each player's own game files, cached locally.
6. **Two kinds of upgrade.** A *tier upgrade* (same item, higher +N, e.g. Hashishin Kavuk +2 → +3; NQ → +1) is a real upgrade. A *new augment on the same item* is only a candidate, because different sets may want different augments.

## Approaches Considered

- **A: Read, flag, write new sets only.** **Chosen** (completeness 6/10, decision dec-4891397d). Full read side; edits to hand-written sets become paste-in snippets; only new and shared sets (and rule cards) are written, to an app-owned file.
- **B: Override layer.** Slot-level changes in a generated file loaded after `get_sets`, verified by an in-game reload. Claude and Codex both recommended it. **Deferred.** Upgrade to B when copy-pasting fixes into existing sets feels too tedious in real use; A's read side carries over unchanged.
- **C: Edit hand-written Lua in place.** Rejected: every player's file style is a new parser case, and editing a shared variable or `set_combine` base can change sets you didn't mean to.
- **D: App-generated job files.** Rejected: importing freezes runtime logic (Doom handlers, Mote modes) into static sets and silently changes behavior.

**Consequence of A:** in hand-written sets, upgrades are flagged with ready-to-paste fixes ("Copy all 4 fixes") but not swapped automatically. Auto-swap does apply to Nexus-owned sets.

## Recommended Approach (A), in detail

### 1. Reading sets: `core/gearswap_reader.py`

- **Find the job files with GearSwap's own lookup, ported exactly.**
  - The name list (`refresh.lua:98-105`): `<Char>_<JOB>`, `<Char>-<JOB>`, `<Char>_<LongJob>`, `<Char>-<LongJob>`, `<Char>.lua`, `<JOB>`, `<LongJob>`, `default.lua`.
  - The directory loop (`pathsearch`, `refresh.lua:684`, loop at `716-729`): `libs-dev`, `libs`, `data/<Char>/`, `data/common/`, `data/`, the `%APPDATA%\Windower\GearSwap` equivalents, then `addons/libs`.
  - **Nesting:** directories are the outer loop and names the inner loop, so `data/<Char>/BLU.lua` beats `data/<Char>_BLU.lua`. In each directory, `include_path()` entries are checked before the plain path.
  - The same function resolves `include`/`require`.
- **Which characters and jobs get scanned:** characters come from the inventory snapshot. For each character, all 22 jobs are tried and the jobs that resolve to a file are listed. Jobs that fall back to a shared `<Char>.lua`/`default.lua` are labelled so.
- **Sub job:** the sandbox mocks the live sub job if the addon reports one for that character and job, else none. A "Sub job" dropdown on the page re-reads with another one, since many files build different sets per sub job.
- **Run each file in a lupa sandbox** (`lupa.luajit21`, because Windower's libs need LuaJIT's `bit`), with a mocked host:
  - Every key in the real `user_env` (`refresh.lua:114-147`) gets a value or a stub, not a guessed subset. That includes `T/S/L/Q`, `empty`, `texts`, `player` (name, main/sub job, level 99), `pet`, `party`, `alliance`, `fellow`, `world`, an empty `buffactive`, `include_path`, `register_unhandled_command`, `equip`, `disable`, `send_command`, `cancel_spell`, `midaction`, `file`, `_global`, `_settings`, a prefilled `sets.naked`, `set_combine`, and `gearswap.res` / `gearswap.pathsearch` / `gearswap.slot_map`. A test keeps the stub list in sync with that block.
  - A `windower` stub: `ffxi_path`, `get_dir`, `ffxi.get_info()`, and no-op `add_to_chat` / `send_command` / `register_event`.
  - `require` behaves like GearSwap's `include_user`, `package.loaded` first. `resources`, `extdata`, `tables`, `texts` and similar Windower libs are preloaded into `package.loaded` as stubs/shared data rather than executed. `res` loads once from Windower's `res/` folder and is shared across files.
  - Disabled: `os.execute`, `io.popen`, `package.loadlib`, and writes. File reads are allowed only under the Windower folder.
  - Guarded: an instruction-count hook stops runaway files.
- **Load like GearSwap does:** run the file body so its functions get defined, then call `get_sets()` (`refresh.lua:167-180`). On Mote files, the job file's `get_sets` includes Mote-Include, which runs `init_include()` → `init_gear_sets()` (`Mote-Include.lua:175, 188`).
- **Walk `sets`** with cycle detection. Record each set path, then each slot's `{name, augments, priority, bag}` (item tables can carry `bag=`, and `augment=` as a singular alias for `augments=`; see `equip_processing.lua:90-94`), normalising slot aliases (`ear1`/`left_ear`, `ring1`/`left_ring`, `range`/`ranged`). A slot set to `empty` is recorded as deliberately empty, separate from not set.
- **Track where combined pieces come from.** The mocked `set_combine` records, for each slot of its result, which argument the piece came from. When that argument is itself a known set path, the slot gets `inherited_from: <path>`. Fixes then target the base set once, instead of producing N lines for N derived sets. Shared piece *tables* (the same Lua table in several slots, e.g. `nova_gear.herculean_helm_9f3a78e3`) are noted as "shared piece definition, used by N sets". No file of origin is claimed until Open Question 5 is decided.
- **Nexus sets listed once.** The sandbox also runs the appended Nexus include, so `sets.Nexus` appears in the walk. Every generated set carries a marker (`_nexus_id`). Marked sets are listed once, from the JSON model, under "Nexus sets", and the walk skips them as Lua sets.
- **Report errors per file** ("SMN couldn't load: `windower.ffxi.get_player` is nil at line 88"). A bad file never stops the others or crashes the page.
- **Cache results** per character/job/sub job, keyed on the modification times of the job file *and every file it included*. Re-read on change or on ⟳. Reading runs off the UI thread.

### 2. Resolving items

- Set names → item IDs through `res/items.lua`, matching English and log names case-insensitively, plus the short names GearSwap accepts (e.g. "Adhemar Wrist. +1").
- Augments → the specific owned copy. Matching is order-independent: split both sides into individual augment strings (the snapshot joins them with ", " and may lead with "Rank N" / "Path: X"), normalise whitespace, case and quote marks, then compare as sets. More than one match, or none, is shown honestly ("2 copies match" / "augments not found").
- **Copies are counted per set.** The same ring or earring in both slots needs two owned copies, otherwise the second cell shows "only 1 copy owned".
- Each piece gets one status: owned and reachable · owned but in an unreachable bag · on another character · not owned. If the set names a `bag=`, that bag is checked too.

### 3. The Set manager page: `ui/pages/sets.py` (see wireframe)

- **Left:** every set from the job's Lua, grouped by batch 1's `PURPOSES`. A keyword classifier maps paths like `sets.precast.WS[...]`, `sets.midcast.Cure`, `sets.engaged.*` and `sets.idle.*`; unmatched paths go to "Other". Badges show counts ("1 upgrade", "Mog Safe ⚠"). Nexus sets get their own group, with "+ New set". Search covers set and item names.
- **Center:** the 4×4 grid. Each cell shows the icon, the name (augment label if the reader knows the variable name, e.g. "(WSD)"), and the bag. Cell states are normal, upgrade available, unreachable, missing, inherited (from a `set_combine` base), deliberately empty (`empty`), and not set. Actions: **Equip now** (the primary action), Compare with guide…, Copy as new Nexus set.
- **Right panel:** the selected slot. The "Owned that fit" tab lists items filtered by character, slot, job and level, with augments and bag; tier upgrades sit at the top. A "Guide pieces" tab is also there. For a hand-written set, choosing an item produces the snippet (`head="Hashishin Kavuk +3",`) with **Copy fix**, **Open file at line** (a best-effort text search for the set path and old item name; falls back to naming file + set), and **Copy all N fixes** when the same old piece appears in several sets. Inherited slots get one fix aimed at the base set, not one per derived set. For a Nexus set, choosing an item edits the set directly.

### 4. Icons: `core/item_icons.py`

- Port of equipviewer's `icon_extractor.lua` (BSD-3, © 2021 Rubenator; base code by Trv). Keep the copyright and license text in the file header and credit it in the README.
- Reads the 32×32 icon for an item ID from the player's FFXI DAT files and writes a PNG cache in the app's user-data folder (`core/paths.py`).
- The FFXI install path comes from the addon: it adds `windower.ffxi_path` to `STATE_UPDATE` (addon version bump). It's remembered for when the game is closed. A placeholder tile is used when the DATs aren't found.

### 5. Upgrade flags

- **Tier upgrades:** same base name with a higher tier (`+1 < +2 < +3`, NQ < +1), owned by this character, wearable by the job. Generalise `tier_family` from `core/gear_guides.py` into a name-based rule that works without a guide entry.
- **Augment candidates:** same item ID, different augments. Shown in the picker as "other copy: …", never badged as an upgrade.

### 6. Nexus sets (app-owned)

- **Model:** JSON per character in the app's data folder. Each set has `id`, `name`, `used_by` (`all` or a list of jobs, where one job is a list of one), `worn` (`normal` | rule), and `slots` (`{item_id, name, augments}`, or `empty`).
- **Set names:** letters, digits, spaces, `-` and `+` only, so no `'`, `"` or `;`. That keeps them safe for `parse_set_to_keys` and in generated Lua. Generated Lua string-escapes them anyway.
- **Generated file:** `GearSwap/data/<Char>-Nexus-sets.lua`, regenerated on save. Its header says "generated by Vana'diel Nexus, edits will be overwritten". It defines `sets.Nexus['<name>']` only when `player.main_job` is in `used_by`, and tags each one with `_nexus_id`. If the player's file already has a `sets.Nexus` table without the marker, the generated file leaves it alone and reports the conflict on the page.
- **Always present:** for every character the app knows, a stub file (no sets, no rules) is written when there's nothing to generate, so the include always finds a file.
- **Loading:** each job file needs one guarded line, **appended as the last line of the file**:
  `pcall(include, player.name..'-Nexus-sets.lua')  -- Vana'diel Nexus`
  - Why `pcall`: GearSwap's `include_user` throws on a missing file (`user_functions.lua:316`), which would stop the whole job file from loading. That can happen when another character loads a shared `<Char>.lua`, `default.lua` or `data/common` file, or when the generated file has been deleted.
  - Errors stay visible: the full line is `local ok, err = pcall(include, …); if not ok and not tostring(err):find('Cannot find the include file') then windower.add_to_chat(123, 'Nexus sets: '..tostring(err)) end`. So only a missing file is silent; a broken generated file still reports in chat.
  - Appending needs no Lua parsing, so it stays within Approach A.
- **What the generated file does at load time (when it's appended, the file body has run but `get_sets` hasn't):** it wraps **only `get_sets`**, keeping a nil original working. Inside that wrapper, after the player's `get_sets` returns, it builds `sets.Nexus` and wraps the event functions (section 7). Waiting matters because Mote/Sel files only define `precast`, `midcast` and the others in `Mote-Include.lua`, which is included from inside the player's `get_sets`. Wrapping is guarded by **function identity**, not a boolean. Each wrapper remembers the function it wrapped and re-wraps whenever the current `precast` (etc.) isn't the Nexus wrapper. That covers a file that calls `get_sets()` again itself: on a Mote file that re-includes Mote-Include, which redefines the events unwrapped, and a boolean flag would silently turn rules off. (`gs reload` builds a fresh `user_env`, so reloads start clean anyway.)
- **Add it for me:**
  - Backs up the file first.
  - Skips the change if the line is already there.
  - Adds a leading newline, so a file without a trailing newline doesn't get joined onto its last line.
  - Syntax-checks the result with lupa, which catches files that end in a top-level `return`.
  - Restores the backup and shows the error if the check fails.
  - **Copy** is always offered as the alternative.
- **After every save,** the app offers **Reload GearSwap**. The addon sends `gs reload`, because a saved file does nothing until GearSwap reloads it.
- New Nexus sets can be worn with Equip now or `//gs equip sets.Nexus['<name>']`. Getting them into automatic swaps is the rule cards' job; the player's own selection logic doesn't know about them.
- **Auto-swap tier upgrades:** in Nexus sets, after the player confirms ("Hashishin Kavuk +3 → update 2 Nexus sets?").

### 7. Rule cards ("When…")

- **One card:** a condition, then "add these pieces on top" or "use this set instead", with a priority.
- **One mechanism:** both shapes compile to "after the player's own swap logic runs, equip this set if the condition holds". A full set (all 16 slots, or every slot the variant defines) behaves as a variant; a partial set behaves as an overlay. Empty slots mean "keep what GearSwap chose".
- **v1 conditions:** buff active (from `res/buffs`, e.g. Doom, Aftermath: Lv.3), weather or day element matches the spell's element (midcast only), HP below N%, pet active.
- **Later:** haste tier. It depends on GearInfo running; reuse the `hasteinfo` path in `resources/Mote_Nexus_Hook.lua` once Open Question 8 is settled.
- **Runtime:** inside its `get_sets` wrapper (section 6), after the player's `get_sets` has run, the generated file wraps `precast`, `midcast`, `aftercast`, `status_change` and `buff_change` (or Mote's `job_post_*`), once, behind the `nexus_wrapped` guard. Rules run in priority order, so the highest priority applies last and wins.
- **Restore:** when a condition ends (`buff_change` gained=false), the runtime re-runs the player's idle/engaged choice. Mote: `handle_equipping_gear(player.status)`. Other frameworks: call the player's `status_change(player.status, player.status)` if defined. Must be tested in game for each framework (Mote, Jason's Someonesmall style, a plain file).

### 8. Extras (all four in scope, sliced below)

- **Equip now:** `gs equip <set path>` (`gearswap.lua:170` resolves any set path, but only within the job file loaded now).
  - **When it's enabled:** only when the live character and main job match the set shown. Otherwise the button reads "Log in as BLU to try this on".
  - **Safety:** the app sends an `equip` request carrying the set path. The addon checks that path and builds the `gs equip` command itself; it never passes a raw string to `send_command`.
  - **Allowed characters:** letters, digits, spaces, `. [ ] ' " : + -` and `_`. Real paths need these, e.g. `sets.precast.WS["Rudra's Storm"]` and `sets.engaged['Aftermath: Lv.3']`.
  - **Quoting:** `parse_set_to_keys` (`helper_functions.lua:380`) has no escape handling, so a bracket key is sent as `['…']` normally and as `["…"]` when it contains an apostrophe. Backslashes are never used.
  - **Rejected:** keys containing both quote types or `]`, plus `;` and newlines anywhere.
  - **To confirm in game:** whether Windower's command line passes double quotes through to GearSwap unchanged (added to The Assignment).
- **Where is each piece:** bag on every cell, unreachable-bag warnings, duplicate-copy notes.
- **Live wearing now:** the addon already sends `equipped` in every `STATE_UPDATE` (`VanadielNexus.lua:339`). The grid can show current gear and the *closest matching set* ("looks like sets.Engaged.Acc, 15/16"). It's labelled a match because GearSwap doesn't record set names at equip time.
- **Compare with guide:** a guide set (batch 1 picker) beside the player's set. One-click copy of owned guide pieces into a Nexus set, or a snippet for a hand-written set.

## Success Criteria

- All eight of Jason's job files (BLU, RUN, SMN, SCH, NIN, COR, BST, RDM) load in the Set manager, or show a clear per-file error. No crash.
